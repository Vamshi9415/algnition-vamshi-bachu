## 5. Observations worth flagging on accuracy/robustness

1. **Microsoft/Bing channel forecasts exactly $0 for all 27 campaigns, all 60 days.**
   Root-caused this: `_build_future_frame()` in `orchestrator.py` builds the future
   feature rows from a single **frozen snapshot** — the *last* training row per
   (channel, campaign) — replicated across the whole horizon, with only calendar
   features recomputed per day. The last Bing training day (2026-06-05) happened to
   have **$0 revenue across every Bing campaign** (see `data/raw/bing_campaign_stats.csv`,
   `TimePeriod == 2026-06-05`), even though Bing revenue was $6,357 in May and >$0 on
   6 of the prior 10 days. Because the lag/rolling features are frozen from that one
   anomalous zero day, every downstream 60-day prediction for that channel collapses
   toward zero. **This is a real methodology weakness, not a crash** — a single
   low-activity snapshot day can flatten an entire channel's forecast. Google and Meta
   didn't hit this because their last training day wasn't simultaneously zero across
   all campaigns. Recommend: base the future-frame template on a trailing average
   (e.g., mean of last 7 days) rather than the single last row, or better, forecast
   recursively day-by-day so lag features update as the horizon progresses.
2. **Prophet component of the ensemble did not run in this environment** — `pip
   install prophet` does not bundle a working CmdStan backend, and building one
   requires a network download, which conflicts with the "no network calls at
   run time" submission rule. A graceful LightGBM-only fallback was added (previously
   this crashed the whole pipeline — see next doc); the ensemble is currently
   effectively LightGBM-only. The 7.04% WMAPE above is therefore LightGBM's
   standalone accuracy, not the documented "60% LightGBM + 40% Prophet" blend.
3. **`roas` has extreme outlier values** (mean 30.9M, max 585B) because it's computed
   as `revenue / (spend + 1e-9)`, which explodes on the many rows with `spend≈0` but
   `revenue>0`. This feeds into `roas_lag*`/`roas_roll_*` training features. Tree
   models (LightGBM) are largely robust to this since splits are threshold-based, and
   it didn't visibly hurt WMAPE, but it's a latent robustness risk and makes the raw
   `roas` column unusable for direct reporting without a floor on spend.
4. **Output granularity is daily, not aggregate-period.** The brief's stated
   constraint is "Forecasts should be aggregate-period forecasts rather than daily
   forecasts" for 30/60/90-day planning windows. The current `predictions.csv` is one
   row per campaign per day; nothing in the pipeline aggregates this into a single
   30/60/90-day total with a P10/P50/P90 range. See the compliance doc for detail —
   this is a brief-alignment gap, not a bug, and would need a (fairly small) new
   aggregation step.
5. **Data leakage check passed after being made real** (previously a no-op — see next
   doc); confirmed empirically that lag/rolling features are correctly `NaN`/shifted
   on the first observation of each campaign series, so the 7.04% WMAPE is not an
   artifact of the model seeing future values.

## 6. Bottom line on "is the accuracy trustworthy"

Yes, with caveats now documented: WMAPE and PICP are genuinely computed on a proper
temporal holdout with no leakage, and are stable across 3 backtest folds. But the
headline numbers come from a run that (a) had to have several pipeline-breaking bugs
fixed first to execute at all on the shipped sample data, (b) is currently
LightGBM-only rather than the documented ensemble, and (c) has at least one channel
(Microsoft) whose forecast is not trustworthy in this run due to the single-day-snapshot
issue in §5. Recommend re-validating WMAPE/PICP after addressing the future-frame
snapshot fragility, since Microsoft's degenerate $0 forecasts don't influence the
30-day *holdout* metric (that's evaluated in-sample per day, not on the frozen future
snapshot) but would materially mislead anyone reading `predictions.csv` directly.
